# План доработки «Клинок Памяти»

Дата: 10.11.2026 · ветка `mp-ui-update` · состояние — по архиву KlinokPamyati.zip

## 0. Что изучено и чего не хватило

- Архив распакован целиком: 1734 файла, 281 МБ. Это RAR, а не ZIP.
- Документы: README, `docs/STATE.md`, `HANDOFF.md`, `CONTINUE.md`, `ROJO.md`, `MCP_SETUP.md`, `plan.docx` (около 75 КБ текста), история git (108 коммитов, 3 ветки).
- Код: 309 Lua-файлов, около 126 тыс. строк. Ключевые серверные системы прочитаны вручную, остальное прошло статический анализ.
- Модели: все 79 GLB (73,9 МБ) разобраны скриптом — треугольники, меши, текстуры, габариты.
- **Ограничения.** В архиве нет плейса (`.rbxl`), папка `map/` пустая, а в песочнице нет Studio и Luau. Поэтому меши, FX-шаблоны и карты внутри плейса не проверены, игра не запускалась. Пункты с пометкой «проверить» нужно подтвердить в Play.

## 1. Коротко

1. **Утёк Notion-токен.** `.mcp.json` с токеном лежит в git минимум в 5 коммитах. Токен нужно отозвать.
2. **Единственная копия мешей, FX и карт — один файл `.rbxl` на рабочем столе.** Из git проект не восстановить.
3. **Одна ошибка при старте сервера останавливает все следующие системы.** На клиенте наоборот: ошибки глотаются молча.
4. **Нет серверной защиты движения.** Телепорт и спидхак проходят, проверка рывка только пишет warn.
5. **Мультиплеер, этажи 3–5, боссы, сундуки v3 и броня ни разу не проверены в Play** (по STATE и HANDOFF).
6. **Код растёт «пакетами-заплатками»:** V2, Plus, 345Kit, Chronicle и т. д. Файлы на 1000–2000 строк, строгой типизации почти нет, около 0,5 МБ мёртвых данных скачивает каждый клиент.
7. **Телефоны:** около 9,3 тыс. деталей на этаж, карта этажа 1 v2 — около 643 тыс. треугольников, все этажи строятся сразу, FPS не мерили.
8. **Для релиза нет:** покупок (ни одного вызова MarketplaceService), настроек, аналитики, недельных заданий и достижений, части врагов из плана. Много пустых id ассетов.

## 2. Что уже хорошо (не ломать)

- Урон, лут и экономику считает сервер. 41 из 43 обработчиков ремоутов идут через RemoteGuard: лимит частоты и чистка аргументов. Оставшиеся два — заглушки.
- `DataService` (переделка 09.11): сессионный замок, UpdateAsync, повторы, BindToClose, миграции. Это выше среднего уровня для Roblox.
- Числа вынесены в `Config/*`, отладочные команды доступны только в Studio, история решений ведётся в STATE и HANDOFF.

## P1. Баги и риски живой игры

### P1-1. Одна ошибка при старте останавливает весь сервер
- **Где:** `ServerScriptService/Bootstrap.server.lua:67–101` — около 25 вызовов `X.start()` подряд без защиты. Порядок важен из-за скрытых хуков (`CombatService.hooks.*`, обёртка `gearStats`). Хаб стартует своими `HubBoot`-скриптами параллельно, и порядок между ними не гарантирован.
- **Проблема:** исключение в одной системе, например в ArmorService, — и не стартуют лут, этажи, сундуки. Игроки попадают в мёртвый мир.
- [ ] Мини-загрузчик: список систем с явными зависимостями. Фаза `init()` (подписки, хуки), затем `start()` (циклы). Каждый шаг — в `xpcall` с traceback, итог в лог и DebugState.
- [ ] Хуки между системами объявлять явно (кто кого расширяет), а не порядком строк. Хаб подключить к тому же загрузчику.
- **Готово, когда:** искусственная ошибка в одной системе не ломает остальные и видна в Output одной понятной строкой.

### P1-2. Клиент глотает ошибки
- **Где:** `StarterPlayerScripts/Bootstrap.client.lua` — около 37 контроллеров в `pcall`. Во всём проекте 241 `pcall`. «Необязательные» модули подключаются через `pcall(require)`, например подконфиги звуков в `Config/Sfx.lua`.
- **Проблема:** ошибка не видна, и молча пропадает кусок игры. Так уже было с клинком, который исчезал из-за ошибки в форме частиц.
- [ ] При ошибке старта контроллера — warn с traceback, счётчик в DebugState, в Studio — заметное уведомление.
- [ ] Убрать `pcall(require)` для своих модулей: модуль либо обязателен, либо подключается по явному списку.
- [ ] Молчаливые `pcall` оставить только вокруг API Roblox: DataStore, покупки, HTTP, загрузка ассетов.

### P1-3. Два реестра ремоутов и «примеры данных»
- **Где:**
  - `Shared/Net/Net.lua` — папка KlinokNet, клиент ждёт её 15 с, после чего может получить nil;
  - `Shared/Net/UiNet.lua` — KlinokUiNet создаётся по месту в `UiNet.ensure` при старте каждой системы, клиент ищет ремоут 3 с и только один раз;
  - `Lib/StationApi.lua:9–34` — показывает MOCK-данные, если ремоута нет.
- **Проблема:** при медленном старте сервера окно получает nil или пример вместо настоящих данных. Ремоут, созданный позже, клиент уже не ищет.
- [ ] Один реестр: все имена в одном файле, сервер создаёт их в самом начале Bootstrap, до `start()` систем.
- [ ] Клиент ждёт без «одного шанса». Если ремоута нет — понятная ошибка, а не пример.
- [ ] Примеры в StationApi — только в Studio и только по отладочному флагу.
- [ ] RemoteGuard не проверяет типы аргументов и пропускает Instance. Это делает каждый обработчик сам — проверить все 43, нужен единый `expect(типы)`.

### P1-4. Нет защиты от телепорта и спидхака
- **Где:** `Systems/CombatService.lua:289–312` — проверка дальности рывка только увеличивает `suspiciousDistances` и пишет warn. Других проверок движения на сервере нет: Floor2Service лишь управляет WalkSpeed для своих замедлений.
- **Проблема:** физикой персонажа управляет клиент. Читер телепортируется к боссу или сундуку, пролетает комнаты, обходит закрытые ворота.
- [ ] Сторож движения на сервере, проверка раз в 0,25–0,5 с: допустимое смещение = скорость × dt + рывок + запас на пинг. При превышении — вернуть на последнюю валидную точку, после N случаев — лог или кик.
- [ ] Проверка зоны: игрок не может оказаться в комнате N+1, пока не открыты её ворота (FloorService знает номер комнаты).
- [ ] Все взаимодействия (сундук, костёр, ворота, станции) проверяют дистанцию на сервере. В DailyService так уже сделано через `nearStation` — повторить везде.
- [ ] Телепорты самой игры (`teleportToZone`, рывки способностей) помечать как легальные, чтобы сторож их не наказывал.

### P1-5. Допуск прицела удлиняет удар
- **Где:** `Systems/MeleeService.lua:50, 56–71` — `AIM_TOLERANCE = 6`: сервер принимает точку удара от клиента в пределах 6 стадов от корня.
- **Проблема:** подменив `aim.origin`, можно бить на 6 стадов дальше дальности оружия.
- [ ] Снизить допуск до 2–3 стадов с поправкой на скорость. Либо считать дальность от серверной позиции, а от клиента брать только направление.

### P1-6. Боевые действия через RemoteFunction
- **Где:** `RequestAttack`, `RequestDodge`, `RequestParry`, `RequestAbility`, `RequestHeal`. Обработчики: MeleeService:404–414, CombatService:691–703, AbilityService:304–307.
- **Проблема:** каждое действие — запрос с ожиданием ответа. Если клиент ждёт ответа перед анимацией, на телефоне с пингом 150–250 мс удар и рывок будут «ватными». Ошибка или задержка обработчика подвешивает поток клиента.
- [ ] Проверить в Studio с эмуляцией задержки 0,2 с: есть ли пауза между нажатием и ударом.
- [ ] Если есть — перейти на RemoteEvent с предсказанием на клиенте: анимация и звук сразу, сервер подтверждает урон или откатывает.
- [ ] Сверить с разделом 12 плана: окна рывка и парирования должны иметь допуск на пинг.

### P1-7. Ежедневная награда может «съесть» день и залипнуть
- **Где:** `Hub/DailyService.lua:83–119`.
- **Проблема:** сначала ставится `busy[player] = true` и записываются `d.streak` и `d.lastDay`, а награды выдаются после, без защиты. Если `EchoService.grantEcho` или `addDust` упадёт, день будет засчитан без награды, а `busy` останется `true` до перезахода.
- [ ] Сначала выдать награды (в `pcall`), потом зафиксировать день. Снимать `busy` в любом случае.
- [ ] После выдачи — внеочередное сохранение.

### P1-8. Профиль: новые поля без миграций
- **Где:** `Systems/DataService.lua:69–151`. Миграции есть только для брони (1→2), талантов (2→3) и сундуков (3→4). Поля `quests`, `archive`, `floorClears`, `armorStash`, `chestsSinceSecret`, `stats.*` есть только в `defaultProfile()`.
- **Проблема:** в профиле, сохранённом до появления поля, оно будет nil, и системы упадут. Например, `publish` читает `profile.stats.chestsOpened` и `profile.materials.rusty_iron`.
- [ ] При загрузке — `reconcile(profile, defaultProfile())`: дописать отсутствующие поля, не трогая существующие.
- [ ] Внеочередное сохранение после ценных событий (босс, сундук, будущие покупки) с паузой 5–10 с. Сейчас при падении сервера теряется до 60–75 с прогресса.
- [ ] Логировать размер профиля (длину JSON) и предупреждать при размере больше 1 МБ. Лимит Roblox — 4 МБ.
- [ ] Автотест миграций на профилях v1, v2 и v3.
- Замечание: в Studio `game.JobId` пустой, поэтому две Studio-сессии с доступом к API считают замок «своим». Учитывать при тестах в Team Create.

### P1-9. Все этажи строятся при старте сервера
- **Где:** `Systems/FloorService.lua:1186–1188` (`F.start()` вызывает `F.build()`) и `1360–1364` (`start()` для каждого этажа).
- **Проблема:** сервер держит в памяти все этажи сразу, даже когда все игроки в хабе. Страдают память, время старта и репликация.
- [ ] Строить этаж при первом входе и разбирать, если на нём никого нет 2–3 минуты.
- [ ] Замерить память сервера (Developer Console → Memory) с 1 и с 6 игроками, до и после.

### P1-10. Обходные решения под конкретную сборку Studio
- **Где:** `Controllers/CameraController.lua:7, 274–323`, `StationController.lua:276`. Сюда же полоски здоровья и метки из деталей вместо BillboardGui.
- **Проблема:** эти решения приняты, потому что в той среде «BillboardGui не рисуется» и «PlayerModule не создаётся». В обычном Roblox оба работают, так что это, скорее всего, особенность среды, где агент снимал скриншоты. Полоски из деталей дороже и прячутся за стенами.
- [ ] Проверить BillboardGui своими глазами в Play и на телефоне. Если работает — вернуть его для полосок и меток.
- [ ] В опубликованной игре проверить, что своя камера и TouchControls не конфликтуют со штатным PlayerModule. Проверить на ПК, телефоне и геймпаде.
